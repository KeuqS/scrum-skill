# Discovery, delivery and transition

Begin with a light discovery conversation: beneficiary/problem, observed evidence
versus assumption, measurable Product Goal outcome, constraints/risks and the first
small feedback experiment. Record unknowns and actual decision owners; no mandatory
giant research phase.

Refine ordered stories with criteria and estimate state. Collaborate on a feasible
Goal/selection/plan using actual capacity. Use [estimation](estimation.md) for points,
Planning Poker and scope history. Build/integrate under actual permissions; inspect
required checks and keep blockers visible. Update status from evidence, not an optimistic chart.

At Sprint close record Done outcomes, real feedback and remaining items; freeze the
metric snapshot before planning another slice. Retrospective selects owned improvements
and inspects earlier actions. Preserve IDs through carryover/splitting; refresh the
handoff/LATEST/master and reconcile actual records on resume.

When deployment/release/transition is requested, record the exact artifact/revision,
environment/configuration, evidence/gaps, actual accountable decision, verification/
recovery results and support/health owner. Acceptance, DoD, source integration,
deployment and release are separate states. An ended effort records achieved/abandoned
goals, outstanding risks and evidence ownership. This is optional operational documentation,
not a new Scrum event or universal gate.

The dashboard is a local inspection aid showing unknowns, changing scope and dates
marked actual/forecast. It does not appoint people, accept work, invent votes or release software.
